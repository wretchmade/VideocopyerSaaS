# VideoCopyer SaaS 测试资源申请与容量依据

日期：2026-10-20。测试目标：5 名同时在线用户、最多 10 个在途视频制作任务，单条成片以 15～60 秒、720p／1080p、30 fps 为范围。AI 图像、视频与规划模型使用外部 API；服务器负责 Agent、任务编排、素材处理、合成和交付。

本次申请确定为 **1 台 8 vCPU／32 GB 内存的常规云服务器，100 GB 系统盘＋500 GB SSD 数据盘，以及同地域 1 TB 标准对象存储预算**。无需 GPU。首轮将本地重任务并发限制为 **1**，另外的任务可以等待外部生成、传输或排队；10 个在途任务不代表 10 路同时合成。该配置用于先部署、再实测，尚不是已经压测通过的容量承诺。

CPU 和内存采用 8C／32G；工作盘和存储额度保留上述容量，因为降低渲染并发不会自动减少历史素材及修订占用。后续按[合成方式优化方案](VIDEO-COMPOSITING-OPTIMIZATION-PLAN.md)验证资源节省，再调整容量和并发。

## 架构决定了服务器承担什么

目标结构为：浏览器 → FastAPI 与统一命令服务 → 项目级 Codex App Server／MCP → D 执行核心 → 外部模型 API、本地媒体处理 → MP4 与剪映包。画布布局在浏览器运行；后台终态事件唤醒 Agent，普通进度不必反复调用规划模型。

按最新[对齐实施记录](PARITY-IMPLEMENTATION.md)，本地协议、模拟供应商返工、工具生命周期和历史数据审计已经通过，本机服务已切换；两轮用户验收、真实模型质量及剪映实机验收仍待完成。这些结果不等同于 5 用户／10 任务上云压测。该轮保留整片合成，没有完成分段编码或本次提出的渲染优化。

| 进程或阶段 | 当前结构及容量含义 |
|---|---|
| Web API | 一个 Uvicorn 实例处理请求、SSE 和协调器。5 名用户的控制请求不是主要计算负载，但跨项目数据库事务和慢工具调用仍需验证 |
| 项目 Agent | 每个活跃项目启动独立 Codex App Server；MCP 模式还启动 Python 工具进程。5 名用户各开两个项目，应按最多 10 组会话预算，不能仅按 5 个进程算 |
| 控制 Worker | 一个带文件锁的后台循环核对、恢复和推进任务；它不是全站唯一的视频执行进程 |
| D Build Worker | 每个构建可启动一个独立 Python 子进程；单个构建内的 ready 节点目前在循环中逐一执行，远端生成会轮询等待 |
| 生成预算 | 原生与旧入口当前都写入 `concurrency=1`；其作用域是相应 D 预算，不是全平台共享模型账号限流器 |
| 本地渲染 | FFmpeg 解码输入为 PNG，Pillow 逐帧合成 PNG，再由 FFmpeg／libopenh264 编码。CPU、工作盘与文件系统缓存是主要资源 |
| 存储与交付 | 本地文件仍是执行输入和恢复依据；COS 是上传与签名访问链路。现有网页文件与成片仍包含应用服务器直接下载路径 |

因此，一个 D Worker 同时推进 **一个构建中的一个节点**；一台服务器上的一个 SaaS 实例可以管理多个 D 子进程。“单进程支持 10 路生成／渲染”不是当前实现的准确描述。跨项目可以出现并行执行，但尚无经过压测的全局资源上限；放任所有构建同时进入渲染会竞争 CPU 和磁盘。

## 单任务与整机容量推导

首轮业务上限设为：全站 10 个在途成片任务、每用户最多 2 个；单项目当前流程只推进一个获授权构建，项目内有依赖的镜头继续顺序执行。供应商在途请求另设全局上限 10，本地重处理另设上限 **1**。两个限制独立，十个成片任务不保证始终都有十个供应商请求运行。这些是待实现并验证的部署限制，修改本文不会自动改变程序并发。

| 阶段 | 建议预留 | 说明 |
|---|---|---|
| 一组项目 Agent＋MCP | 0.5～1 GB 内存；规划响应时存在 CPU 短峰值 | 按最多 10 组预留 5～10 GB；实际模型推理在外部服务 |
| 一个等待生成的 D Worker | 0.15～0.4 GB 内存，少量 CPU | 按 10 个预留 1.5～4 GB；下载、解码开始后转入重任务预算 |
| 一个 1080p 本地重任务 | 2～4 vCPU、2～4 GB 内存、10～20 GB 临时空间 | 包含解码、Pillow、编码或较重导出；复杂网页捕获／品牌贴图可能超出，需归入同一资源池 |
| 系统、API、控制器、数据库 | 4～6 GB 内存，并保留 CPU 给交互 | 测试期数据库可同机；另保留文件系统缓存及突发余量 |

为避免重复计数，按 10 组 Agent、9 个轻量等待 Worker、1 个包含其 Worker 与子进程的重任务、基础服务计算，预计约 **12.35～23.6 GB** 工作内存；32 GB 余下约 8.4～19.65 GB 供文件缓存和突发使用。这是保守预算，不是 RSS 实测。活跃会话超过 10 组或单任务超出上述规格时，需要排队或另行提高资源配额。

8 vCPU 中，先将一个重任务的完整进程树限制为最多约 4 vCPU，余下供 Agent、API、数据库与传输。需实现进程／容器 CPU 限制和 FFmpeg 解码、滤镜、编码线程控制；单个 `-threads` 参数不能替代整个任务的资源限制。较重导出和捕获也共享该重任务名额。

以房间样本粗估相同复杂度的 60 秒 1080p 中间帧占用：

`0.686 GB × (60 ÷ 18.8) × (1920×1080 ÷ 720×1280) ≈ 4.93 GB`

这是按时长与像素数线性缩放的场景估算，PNG 压缩率和图层数量不会严格线性。每任务为输入、输出、导出和一至两次返工预留 25～30 GB，10 个任务约 250～300 GB；500 GB 工作盘留出数据库、缓存及空间余量。源素材远大于输出规格、复杂多层或更长视频应单独提高配额。

按当前样本的 55 秒渲染时间，**如果**云上同样达到该速度，1 个渲染槽对同时到达的 10 条同类短片需约 10 批、550 秒才能全部完成本地渲染；最后一条约排队 495 秒。这不含外部模型和传输等待，且不能作为 60 秒 1080p 任务的时间承诺。首期接受渲染排队，页面须明确显示排队状态。

| 资源阶段 | 用途与限制 |
|---|---|
| **本次申请：8 vCPU／32 GB＋500 GB SSD** | **5 用户、10 任务在途，本地重任务并发 1；作为部署和优化的测试基线** |
| 后续升配候选：16 vCPU／64 GB | 仅在优化后压测表明 CPU／内存不足，或排队时间不能接受时评估；并发需重新验证 |

不要为当前远端模型工作流申请 GPU 实例。只有后续实际引入本地模型推理或已经适配的 GPU 编码／处理链路，GPU 才能改变容量。

## 对象存储与全球网络配置

**首选 COS 的原因是现有代码已接入腾讯 SDK 和 COS 预签名链路**，并非认定 COS 性能必然优于 TOS。[SaaS 存储代码](../server/local/storage.py)直接使用 `qcloud_cos`；[D 存储边界](../server/app/workbench_d/commercial/storage.py)接受 `local` 与 `cos-presigned`。TOS 虽有 S3 Endpoint，也不能据此认定当前腾讯 SDK 可直接替换，需要完成独立适配和契约测试。

腾讯 COS 官方地域表包含新加坡 `ap-singapore`、香港及欧美地域；在首期用户地域未知、现有模型链路位于亚洲的情况下，推荐新加坡作为全球测试的单一源站。若测试者主要在欧美，应重新比较相应地区的应用响应与模型访问。单地域服务器不等于全球低延迟或高可用。[COS 地域与 Endpoint](https://www.tencentcloud.com/document/product/436/6224)

当前火山引擎 TOS 官方地域表列有香港 `cn-hongkong`、柔佛 `ap-southeast-1`、雅加达 `ap-southeast-3`；不能把 `ap-southeast-1` 当作新加坡。最终以供应商账号实际可开通的地域及配套 ECS 为准。[TOS 地域与访问域名](https://docs.volcengine.com/docs/TorchObjectStorage/Regionsandendpoints?lang=zh)

Bucket 使用标准存储、私有读写。建议按用户、项目和资源类型分前缀，保存原始素材、生成素材、成片、剪映 ZIP 与恢复备份；临时 PNG 主要留在 SSD，避免把几千张工作帧全部上传。必须依据引用关系和构建状态清理，不能删除未完成任务的断点或仍被修订引用的素材。

测试保留策略建议为：未完成分片 1 天清理；无引用临时对象 7 天；普通测试素材和交付 30 天；已验收且可重新生成的本地中间帧 24～72 小时清理；数据库／工程备份按日保留 7 份、按周保留 4 份。正式指定保留的样片独立前缀豁免自动过期。生命周期只能作为安全清理的执行手段，不能代替应用对资产引用和用户保留意图的判断。

1 TB 是初始存储预算而非由并发数唯一决定的容量。举例：每天 50 个完成任务，每任务长期保留 0.3 GB，保留 30 天，则约 `50×0.3×30=450 GB`；另留备份、版本和素材余量。如果只偶尔做 10 条测试片，实际用量会低得多；如果平均每任务保留 1 GB，则同样频率已需 1.5 TB。

全球媒体访问建议走浏览器直传对象存储、签名下载或带用户鉴权的 CDN。跨洲上传可评估 COS 全球加速，播放下载可评估 CDN；两者不是同一项，均要分开预算。腾讯官方也区分上传较多与下载较多的选型。[COS 全球加速说明](https://www.tencentcloud.com/document/product/436/33409)

当前应用需要补齐直传／直链、对象存储回读和前端 CSP 允许域名后，才会实际卸载服务器媒体流量。不能因为申请了 COS，就假定 MP4 和 ZIP 已自动通过 CDN 分发。

网络量级可按当前编码参数检查：720×1280 默认目标视频码率约 7.37 Mbps，1080p 约 16.59 Mbps。5 人同时直接从服务器看 1080p 视频，视频部分即约 83 Mbps，100 Mbps 出站已接近饱和；因此 100 Mbps 是测试申请上限的起点，媒体直出对象存储很重要。30 Mbps 只适用于已经完成媒体分流的控制服务，不能作为当前整站代理播放的配置。

## 部署前需要完成的事项

1. **多用户隔离。** 当前 `OWNER='local-owner'`，Host／Origin 限于 localhost。应完成登录、用户到项目的权限映射、用户预算与签名访问授权，再进行 5 名真实用户的公网测试。反向代理改写 Host 不能代替这些能力。
2. **Linux 配置迁移。** 当前媒体密钥从 Windows PasswordVault 读取，启动脚本和部分运行时路径为 Windows 环境。需改为云端服务身份／密钥注入、Linux 服务启动和可用字体。FFmpeg 必须含项目使用的 `libopenh264` 并符合当前运行时核验；不能直接假设默认系统包能通过。
3. **全局资源调度。** 为所有生成入口设置同一模型账号限流，为所有解码／渲染／较重导出／捕获设置重任务配额，避免工具直调绕过队列；停止和恢复时保留租约与幂等语义。首轮 10 个制作任务、**1 个重任务**；任务级并发、供应商并发与 CPU 配额分别管理。
4. **单 API 进程先验。** 当前 Agent 会话和协调状态含进程内对象，启动时还会执行恢复；不能简单加 `uvicorn --workers 4` 当作横向扩容。首期单 API 实例＋独立控制 Worker＋受限 D 子进程即可。
5. **数据库与备份。** 控制层已有 PostgreSQL 配置路径但仍待环境验证，D 执行库仍为每项目 SQLite。首轮可验证同机 PostgreSQL 控制库与本地 SSD 上的 D 库；不把 SQLite 放进 COS 或对象存储挂载盘。数据库／工程／素材备份需保持可恢复的一致性，不能只复制活动数据库文件。
6. **供应商配额。** 确认实际模型账号至少 10 个并发处理中任务，查询轮询建议 5～10 秒并加抖动。按 10 路每 5 秒查询一次约为 2 QPS；仍需与账号其他业务共享限流。Seedance 2.5 当前官方默认并发表为企业 10、个人 3，但本项目也使用 Seedance 2.0，应逐模型查账号实际配额，不能跨模型套用。[模型限流说明](https://docs.volcengine.com/docs/ark/seedance-2-5?lang=zh)
7. **交付边界。** 云端输出可下载的剪映包；用户电脑上的剪映安装、打开、编辑和保存由客户端承接，不由云服务器路径替代。

## 测试验收与扩容依据

先用已有素材验证 1 路重任务，再用模拟供应商验证 5 名用户各提交 2 个任务、单槽排队、同时下载／播放、停止／续作、进程重启与旧结果晚到。1 路通过后，在隔离压测环境评估 2 路，不直接提高线上限制。最后在单独授权的 API 预算下做真实 10 路在途任务测试；模拟轮询无法证明真实供应商并发或跨境素材抓取成功。

必须记录进程树峰值 RSS、CPU、磁盘读写与队列、每任务临时磁盘峰值、渲染耗时、排队耗时、API p95、供应商等待、对象存储传输与错误率。首轮目标可设为：CPU 持续低于 75%、内存低于 75%、工作盘空闲超过 25%；控制 API p95 低于 1 秒、停止确认低于 2 秒，以上响应目标不含模型思考和远端取消完成时间，全球访问另按地区测量。

只有 2 路隔离压测也通过上述交互和资源指标，才考虑把本地重任务并发由 1 调为 2。若 CPU／IO 已满，先按合成优化方案减少重复处理，再决定升配或拆出渲染 Worker；若主要时间在供应商排队，升级服务器不会明显缩短总时长。首期单机用于测试，不提供高可用承诺。
